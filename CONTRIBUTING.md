# Contributing to Gustaf

Thanks for helping. This page covers setup, checks and how changes get into a release. The code layout is described in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), features in [docs/README.md](docs/README.md).

## Prerequisites

- **Node.js** in the version from [`.nvmrc`](.nvmrc) (currently 22; `nvm use` picks it up) and npm.
- **Rust** stable toolchain ([rustup](https://rustup.rs)).
- **Tauri 2 prerequisites** for your OS ([official guide](https://v2.tauri.app/start/prerequisites/)):
  - macOS: Xcode Command Line Tools. This is the platform the app is developed and tested on.
  - Windows: Microsoft C++ Build Tools and WebView2 (preinstalled on current Windows).
  - Linux (Debian/Ubuntu names, as used in CI): `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev patchelf libssl-dev libdbus-1-dev pkg-config libxdo-dev libxcb1-dev libxrandr-dev libgbm-dev libegl-dev libpipewire-0.3-dev libspa-0.2-dev libclang-dev libwayland-dev`. Release builds use Ubuntu 24.04.
- Optional: Google Chrome for the end-to-end tests (they skip with a message without it), the `codex`, `claude` or `cursor-agent` CLIs to try CLI providers, `gh` for the pull request flow.

## Setup

From the repository root:

```sh
npm ci                                   # all workspaces (apps/desktop, packages/protocol) from the root lockfile
npm --prefix apps/desktop/sidecar ci     # the Node sidecar has its own lockfile and is bundled with its node_modules
```

The sidecar is deliberately not a workspace member; see [README → Development](README.md#development).

## Run

```sh
npm run tauri dev       # native app with hot reload
```

`npm run dev` serves only the frontend in a browser, without the Rust backend, so chats do not work there. The canvas runtime is generated by the `predev`/`prebuild` hooks; if you only run tests, build it once with `node apps/desktop/scripts/build-canvas.mjs`.

## Checks

Run before every pull request:

```sh
npm run check
```

It runs, in `apps/desktop`: the i18n key check (`en` and `ru` must match), `tsc --noEmit`, the Node unit tests (`node --test tests/*.test.mjs`), the Vitest UI tests, the end-to-end tests (production build in Chrome against a fake backend) and `cargo test`; then `packages/protocol` typecheck and tests. CI runs the same on macOS, Windows and Linux. Focused suites: `npm run test:chat -w apps/desktop` (also `test:canvas`, `test:usage`, `test:cli`, `test:csp`). Release scripts: `npm run version:check` and `npm run test:release`.

Add or update tests with every behaviour change. If a change cannot be tested automatically, say in the pull request how you checked it, and what you did not check.

## Branches and releases

`dev` is the integration branch and the default target; `main` only receives releases and hotfixes. Details: [docs/branching.md](docs/branching.md) (branches, CI) and [docs/release.md](docs/release.md) (release flow, hotfixes, signing).

1. Branch from `dev` (`feature/<topic>`; agent branches use `gustaf/<topic>`) and open a pull request **into `dev`**. CI must pass.
2. A release bumps the version on `dev` (`npm run version:bump -- patch|minor|major`), then a pull request from `dev` into `main`.
3. The push to `main` builds all installers, tags `vX.Y.Z` and creates a **draft** GitHub Release. Do not push version tags by hand. Before the draft is published by hand, the [release checklist](docs/release-checklist.md) is run on the built artifacts.
4. Hotfixes branch from `main`, go back into `main` by pull request, and `main` is then merged back into `dev`.

Do not push directly to `dev` or `main`.

## Commits and pull requests

- One topic per pull request; keep unrelated refactors out.
- Commit messages: a short imperative subject (`Add per-hunk accept to the diff view`), a blank line, then the why if it is not obvious.
- Fill in the pull request template: summary, motivation, how you tested (`npm run check` output), screenshots for UI changes.
- Update the docs that describe the behaviour (`README.md`, `docs/features/*.md`) and add a line under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md) for user-visible changes.
- Never commit API keys, tokens, `.env` files, signing keys or logs containing them. Test fixtures use fake values.
- UI strings go through the i18n dictionaries in `apps/desktop/src/i18n/` (both `en.json` and `ru.json`).
- Internal names are `gustaf` everywhere: the bundle identifier and Keychain service `io.github.libes6.gustaf`, the crate `gustaf` (`gustaf_lib`), the npm packages `@gustaf/*`, the project folder `.gustaf/`, the `gustaf://` pairing scheme and the `gustaf-*` text protocols. Builds from before the rename used `mcode` names; they are only read as fallbacks (`src-tauri/src/legacy.rs` moves the old app data folders once at startup, `secrets.rs` moves old Keychain entries on first read, `src/lib/projectFolder.ts` falls back to `.gustaf/`). Do not add new `mcode` names.

## Where tasks live

The maintainer's backlog is a local `TASKS.md` that is ignored by git and not part of the repository. For contributors, [GitHub Issues](https://github.com/Libes6/Gustaf/issues) are the place for bugs and feature requests; please open or comment on an issue before starting a large change. Security problems go through [SECURITY.md](SECURITY.md), never a public issue.

## Mobile app

`apps/mobile` is an Expo companion app **skeleton** that runs against an in-memory mock (no desktop server exists yet). It is not an npm workspace: it has its own `package-lock.json`, and root `npm ci` / `npm run check` do not touch it.

```sh
cd apps/mobile
npm ci
npm run check        # tsc --noEmit + node --test (what the CI "mobile" job runs)
```

Running it on a device needs a development build (`npx expo run:ios` with Xcode, or `npx expo run:android`). Details: [apps/mobile/README.md](apps/mobile/README.md).
