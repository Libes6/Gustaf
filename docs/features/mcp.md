# MCP servers

Part of the [M Code documentation](../README.md).

Settings, MCP servers: connect [Model Context Protocol](https://modelcontextprotocol.io) servers and the agents of **API providers** (OpenAI, Anthropic, Gemini, OpenRouter, local models) can use their tools. **Claude Code, Codex and Cursor Agent use their own MCP configuration; M Code does not inject servers into them** (the list is not shared with them either).

- **Servers:** local servers over stdio (`command`, `args`, `env`, optional working directory; started from an argument array, never through a shell, with the login-shell `PATH`, so `npx`/`uvx` work) and remote servers over streamable HTTP (`url`, `headers`; JSON and SSE responses; `https://`, or `http://` to localhost). The legacy SSE transport is not supported. Each server is global or bound to one project, and can be disabled. Paste an `mcpServers` JSON block (Claude Desktop, Cursor, VS Code shape) with "Import JSON", or load `~/.cursor/mcp.json`.
- **Secrets:** env values and headers marked "Secret" (ticked automatically for names like `*_TOKEN`, `Authorization`) are stored in the macOS Keychain (`mcp:<server id>:env|header:<name>`), never in the settings database, and are removed with the server.
- **Lifecycle:** a stdio server starts on first use (or "Test connection"), does the `initialize` handshake, and is restarted with backoff if it crashes (at most 5 crashes in a row, then "Error" until started again). It is killed when disabled, edited, removed or when the app quits. Messages are capped (16 MB in, 4 MB out), every call has a timeout (60 s by default, per server), stderr goes to a bounded log shown under "Log". `notifications/tools/list_changed` refreshes the tool list.
- **In the agent:** tools are offered as `mcp__<server>__<tool>` (at most 64 characters, collisions get a numeric suffix) with their JSON Schemas sanitized and size-capped. Main agent only (subagents keep their fixed tool set). Results (text, one PNG image, resource links, embedded text resources) become tool results capped at 50,000 characters; other binary content is replaced by a note.
- **Approvals:** every call asks by default (Full access does not skip it). "Always allow" can be set per tool (also from the approval card) or per server. In read-only mode only tools you marked "Read-only" are offered and callable; hints from the server are shown but not trusted. Calls appear in the action log as `mcp__<server>__<tool>`. Tool output is untrusted data and the system prompt says so.

- **Cancellation:** stopping a run cancels the `tools/call` that is in flight. Stdio: the call returns at once and Rust sends `notifications/cancelled` with the request id and drops the pending entry, so an answer that still arrives is ignored. HTTP: the request is aborted, the client returns at once and posts `notifications/cancelled` (best effort); the server's late answer is never read. Timeouts send the same notification.
- **Resources:** a server that announces the `resources` capability gets two built-in agent tools, `mcp__<server>__mcp_list_resources` (one line per resource) and `mcp__<server>__mcp_read_resource` (`uri`). They follow the tool rules: every call asks unless allowed ("Always allow" and "Read-only" are set under the server's Tools, where both appear as built-in rows named `mcp_list_resources` / `mcp_read_resource`; in read-only mode only those marked read-only are offered). `resources/read` text is capped at 50,000 characters, one PNG up to 5 MB is attached, any other binary content is replaced by a note with its size. The resource list is cached until `notifications/resources/list_changed` (no subscriptions). Resource templates are not listed; any URI the server accepts can be read. Content is untrusted data.
- **Prompts:** the composer's attach menu has "MCP prompt…" when a server is configured. The dialog lists the prompts of enabled servers that announce `prompts` (global ones and those of this project), asks for the arguments, and only on "Insert" calls `prompts/get`; the rendered messages' text goes into the composer (a single user message as is, otherwise with User/Assistant prefixes, capped at 20,000 characters). Prompts are never offered to the model and nothing is sent automatically. `notifications/prompts/list_changed` refreshes the cached list.
- **OAuth (HTTP servers):** tick "Sign in with OAuth" in the server form (optional client ID and scope), then "Sign in" in the list. Flow per the MCP authorization spec (2025-06-18): an unauthenticated request gets the 401 challenge (`WWW-Authenticate: resource_metadata`), then protected resource metadata (RFC 9728; its `resource` must cover the server URL; servers without it use their own origin as the issuer), authorization server metadata (RFC 8414 and OpenID Connect locations; the `issuer` must match and `S256` PKCE must be advertised, otherwise sign-in is refused), dynamic client registration (RFC 7591, public client) unless a client ID is configured, an authorization URL with `state`, `code_challenge` (S256) and `resource` (RFC 8707), opened in the system browser through the opener plugin. A Rust listener on `127.0.0.1:<random port>/callback` receives the redirect (state compared, Host checked, 5-minute timeout, cancelled by "Cancel"); the code is exchanged with the exact same redirect URI and the verifier. Every discovered endpoint must be `https://` (http only for localhost). Tokens and the registered client live in the Keychain entry `mcp:<id>:oauth` (JSON), never in settings or logs; an `Authorization` header configured by hand is replaced by the OAuth token. The token is refreshed shortly before it expires and, once, after a 401 (one refresh at a time; `invalid_grant` deletes the tokens and asks to sign in again). "Sign out" deletes the Keychain entry (no revocation request is sent). Changing the URL or client ID, turning OAuth off, or removing the server deletes the tokens. Without the legacy fallback of the 2025-03-26 spec (guessed `/authorize`, `/token` endpoints) a server with no discoverable metadata cannot be signed in.
- **HTTP scope and OAuth:** discovery, registration, token and refresh requests go through the HTTP plugin, so they must be inside the `http:default` scope: `https://*` covers every https authorization server (also with a port) and loopback http covers a local one; the sign-in is stricter than the scope and refuses plain http authorization endpoints even for the private ranges the scope allows. Opening the browser uses `opener:allow-default-urls`, and the Rust listener is an app command. `tests/csp.test.mjs` checks the scope against representative OAuth endpoint URLs. See [security](security.md).

Not implemented: sampling, elicitation, roots (answered with an empty list), resource subscriptions and templates, the legacy SSE transport, the 2025-03-26 OAuth endpoint fallback, token revocation, subagent access to MCP tools, CLI providers (own config). The OAuth flow has only been exercised against fakes, not a real provider, and nothing here was smoke-tested in `tauri dev`.

Logic: `src/agent/mcp/` (`config.ts`, `protocol.ts`, `toolset.ts`, `resources.ts`, `prompts.ts`, `oauth.ts`: pure; `oauthFlow.ts`: sign-in/refresh over injected dependencies; `http.ts`: HTTP client over an injected `fetch`; `runtime.ts`: settings, Keychain and connections), `src-tauri/src/mcp.rs` (stdio runtime), `src-tauri/src/oauth.rs` (loopback redirect listener), `components/McpServers.tsx` and `components/McpPromptDialog.tsx` (UI).
