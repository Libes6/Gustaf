# Subagents and background agents

Part of the [Gustaf documentation](../README.md).

With a writable project (not read-only mode) and a model with tool support, the main agent can start subagents with the `spawn_agent` tool (`title`, `prompt`, `type`, optional `files` and `model`). A subagent is a separate agent run: its own history (it cannot see the chat), its own model (see below), a tool allowlist by type and a budget. The main agent receives only a final report of at most 8,000 characters. Several `spawn_agent` calls in one turn run in parallel; at most 3 run at once (the limit is shared by all chats), the rest wait in a queue.

- **Types:** `explore`, `plan` and `review` are read-only (`read_file`, `list_dir`, `search`) and run in the main agent's current workspace; `general` can also edit and run commands. A subagent cannot start subagents.
- **Models (Settings, Usage, Agents):** a default model per type, else the chat's model. The main agent may pass `model` (`provider/model`, or a model id that is unambiguous) only for a model on the "Models agents may request" list, a type's model or the chat's own; anything else is refused as a tool error. Only API providers whose model supports tools can run a subagent through `model` (a CLI agent such as Codex, Claude Code or Cursor runs its own tools: name it with `provider` or `role`, see "Mixed providers" below); an unavailable model falls back to the chat's model with a note in the transcript and the report. The same page sets a cheaper model for chat compaction and generated commit messages (falls back to the chat's model when it is missing).
- **Isolation:** a `general` subagent always works in its own shadow copy of the project (same linked directories and setup command as the chat's copy, made from the original project, so it does not see edits the main agent has pending). Its changes show up as a separate pending review in Changes; nothing is applied until you accept. When two pending reviews of the project change the same file (two subagents, or a subagent and the main agent), the later report carries a warning naming the other one and the files, and the earlier run shows it too.
- **Budgets per run** (defaults: explore/review 20 steps, 40 tool calls, 5 min, 600k tokens; plan 15/30/5 min/500k; general 40/80/15 min/1.5M; each field can be changed per type in Settings, Usage, Agents, under hard caps): when one is exceeded the run is stopped, the transcript gets a "Stopped at its … limit" note and the report says which limit, with whatever the agent had said last. Subagent tokens also count toward the day and chat budgets: their replies are not stored as chat messages, so they are added per local day and per parent chat in the `agentUsage` setting (31 days, 300 chats) and summed into the budget gauge.
- **Plans (`delegate_tasks`):** the main agent submits up to 12 tasks (`id`, `title`, `prompt`, `type`, optional `files`, `dependsOn`, `model`). Tasks run in parallel up to the concurrency limit; a task starts only after its dependencies finished and gets their reports appended to its prompt (their file changes stay in their own pending reviews, so it does not see them in its copy). Two `general` tasks whose `files` overlap (same file, or a folder containing it), or that declare no files, never run at the same time: the later one waits. When a task fails, hits a limit or is cancelled, the tasks depending on it are skipped (setting "Cancel dependent tasks when one fails", the call can override it with `cancelDependents`). Invalid plans (duplicate ids, unknown dependencies, cycles, a model that is not allowed) are refused before anything starts. The main agent receives one merged message: a status line per task and the bounded reports.
- **Retries (`delegate_tasks`):** the call may set `retries` (0 to 2, default 0; anything else is a tool error). A task that ends `failed` (an error, not a limit stop, a budget stop or a cancel) is run again after a short pause (1 s, then 3 s), as a new run titled "<title> (retry N)" and, for a `general` task, in a fresh private copy; the failed attempt's partial changes are rejected (not left as a pending review). Dependants wait for the retries and get the final report. The merged summary says how many attempts each task took ("completed, 3 attempts") and the retry allowance.
- **Budget stop:** when the day or chat token budget (Settings, Usage, Budgets; subagent tokens count through the ledger) is exceeded, running subagents are stopped at their next step with the status "Over budget" (`budget`; the report says which budget), queued ones end as `budget` without starting, and `spawn_agent` / `delegate_tasks` are refused with a tool error naming the budget. Switch "Stop agents when over budget" (Settings, Usage, Agents, `agentSettings.stopOnBudget`, default on) off to keep budgets as warnings only. Everything else (the banner, the main agent) is unaffected. Usage is read at most every 5 s (stored messages) plus the live ledger; unreadable usage never stops anything.
- **Commands and approvals:** subagents go through the same command rules as the main agent. Deny rules block unchanged, and "ask" requests (including the shadow-copy setup command) appear as the usual approval card with a "Subagent: <title>" line, one at a time. While a request is open the chat shows a "!" badge in the sidebar (for any approval, also from the main agent), so a waiting agent in another chat is visible. Tokens are recorded like any other turn.
- **Notifications:** while Gustaf is in the background, a background agent that finishes, fails or stops at a limit, and any new approval request, sends a system notification (`tauri-plugin-notification`), bounces the dock icon and raises the dock badge count; focusing the window clears the badge. Can be turned off in Settings, Usage, Agents. Stopped runs do not notify.
- **Background tasks column:** a full-height rounded column at the far right of the chat layout (340 px, part of the layout: the chat shrinks, nothing overlays the composer), laid out like the "Background tasks" pane of Claude Code desktop. Header: the title and two icon buttons, Expand (the column covers the whole chat area; the button toggles back) and Close (also Escape inside the column; focus returns to the toggle). It opens from a toggle button at the top left of the chat (bot icon with the number of running agents; shown once the project has any agent) and by itself the first time a new agent starts running (once per run; closing it is respected until the next new run; agents already running when the chat view was created do not open it). It lists the multi-agent runs themselves: our own subagents (`spawn_agent` / `delegate_tasks`, from SQLite) and the CLI-native subagents of Codex and Claude Code, an entry as soon as the spawn event arrives. Space rules: below 1100 px window width the sidebar folds away while the column is open (as it does for the canvas), so the chat keeps at least about 450 px at the minimum window width of 900 px; with the canvas pane open too, the canvas takes its share of what the column leaves, and below a 1500 px window width the column floats over the canvas pane (never over the chat; close it to reach the canvas); the file-review panel lives inside the chat area and simply shrinks with it. Each run is a card per run (bold title wrapping over up to four lines, a muted "Agent · type" line with the elapsed time next to it, a line with model, tokens and tool uses, a muted current-step line with a "View transcript" link, a square Stop button at the right), a "Running" section, then a collapsible "Finished N" row (folded while something runs, open otherwise) with a trash button that clears the finished ones. The current step is "Waiting for approval" while an approval is open. The transcript dialog (the full stored messages, loaded when it opens and refreshed every 2 s while the run is active: the task, text, each tool call with its stored result, notes, the report) and, for a finished, failed, limit- or budget-stopped run, "Continue this agent". Stopping the main agent stops its subagents.
- **Persistence:** runs live in SQLite (`agent_runs`: id, chat_id, title, type, model, status, started_at, ended_at, tokens, tool_uses, error, report, plus provider, project, created_at, changed files and warnings; `agent_messages`: run_id, seq, role, parts_json, created_at), created by the idempotent schema in `src-tauri/src/db.rs`. Every message of a subagent (seq 0 is the task prompt) is written as it happens, bounded per message (text and results 8,000 characters, tool arguments 4,000, 48,000 per message, images dropped, secrets scrubbed like exported chats); at most 2,000 messages per run. Retention: the newest 200 finished runs plus every active one (older runs and their messages are deleted when a run is created); "Clear finished" deletes rows; deleting a chat deletes the runs it started. Runs that were queued or running when the app quit load as interrupted (and are marked in the table). The old `agentRuns` setting (50 runs with clipped steps) is migrated once into the tables (flag `agentRunsMigrated`, then the setting is emptied); migrated steps show as one message each.
- **Continue this agent:** the button (row and transcript dialog) takes a follow-up and puts a request into the chat's message box (editable, not sent): the main agent then calls `spawn_agent` with `continue_from` = the run id. The new run is seeded with a bounded summary of the old one (its task, the newest 40 tool calls, how it ended, its report) and the follow-up as its task, and runs as a normal new run (the old transcript is not replayed). Only `completed`, `failed`, `limit` and `budget` runs qualify (not running, cancelled or interrupted ones); an unknown or unfit id is a tool error. `delegate_tasks` does not take `continue_from`.

Logic: `src/agent/subagents.ts` (runtime), `subagentCore.ts`, `orchestrator.ts`, `agentSettings.ts` and `scheduler.ts` (pure: arguments, allowlists, budgets, model choice, plans, ownership, overlaps, reports, queue), `agentSettingsStore.ts`, `agentRuns.ts` / `agentRunsDb.ts` / `agentRunsModel.ts` / `agentTranscript.ts` (store, SQLite statements, the pure run model with the token ledger, and the pure transcript helpers), `lib/budgetUsage.ts` (budget check for the stop), `lib/modelRouting.ts`, `lib/attention.ts`, `components/AgentsPanel.tsx` (`AgentsToggle`, `AgentsColumn`), `lib/useBackgroundTasks.ts` (open/expand state, auto-open per new run), `components/CanvasWorkspace.tsx` (places the column), `components/AgentSettingsSection.tsx`; tests: `tests/scheduler.test.mjs`, `subagentCore.test.mjs`, `orchestrator.test.mjs`, `agentSettings.test.mjs`, `agentRuns.test.mjs` (also against a real SQLite via `node:sqlite`), `agentTranscript.test.mjs`, `followUps.test.mjs`, `ui/AgentsPanel.test.tsx`, `e2e/tasksLayout.test.mjs` (real Chrome: the column at 900 and 1700 px, with and without the canvas, expanded) and `subagents.test.mjs` (the real agent loop with a scripted model and fake shadow copies).

## Mixed providers: CLI agents as subagents

`spawn_agent` and each `delegate_tasks` task may name a `provider` (a provider id from Settings, an exact name also works when it is unique) or a `role`. Without either, nothing changes: the type's model, the chat's model, the API subagent loop above.

- **Allow-list (Settings, Usage, Agents, "Providers agents may request").** A task may name the chat's own provider, the providers of the type defaults and of the allowed models, and the providers on this list. Anything else, an unknown or disabled provider included, is refused as a tool error before anything starts; for `delegate_tasks` the whole plan is refused, so no task has started when you see the error. The tool description names the allowed providers (CLI agents are marked) and the roles that can be used. With `provider`, `model` is that provider's model id (a CLI's own `default` when omitted; for an API provider the first listed model with tool support); any model of an allowed provider may be named, the model allow-list applies to `model` without `provider`.
- **Roles (Settings, Usage, Agents, "Agent roles and providers").** Four presets, planner, implementer, reviewer and tester, each a provider and model. A task names `role` instead of `provider` / `model` (combining them is a validation error). An unknown role name is a validation error like any other plan error; a role without a preset, or whose provider is no longer enabled or no longer on the allow-list, is refused before anything starts. Picking a provider for a role in Settings adds it to the allow-list (your decision to allow it); removing it from the list later makes the role unusable again. Roles do not change the task `type`, which stays explicit.
- **Which CLIs.** Codex, Claude Code and Cursor Agent accounts (provider kind `cli`) run through the same adapter as chat runs, non-interactively (`codex exec`, `claude -p`, `cursor-agent -p`). The Cursor SDK provider (kind `cursor`) is refused with a clear error: its sidecar takes no access level, so it could be neither kept read-only nor sandboxed.
- **Access.** Read-only types (`explore`, `plan`, `review`) use the CLI's own read-only flags (Codex `--sandbox read-only`, Claude `--permission-mode plan`, Cursor `--mode plan`) and run in the parent's folder (so a review sees uncommitted edits; this is a deliberate difference from a worktree for every task). `general` is capped at "auto" access (Codex `workspace-write`, Claude `acceptEdits`, Cursor without `--force`), never "full" / sandbox bypass, whatever the chat's access is. The CLI gets no Computer Use and no app tools. Nobody can answer a prompt from the CLI, so the system text tells it to never wait for approval; actions the CLI's own permission mode does not allow are simply denied by the CLI. The app's command rules and hooks apply to the app's own tools only, not to what a CLI runs inside its sandbox.
- **Isolation.** A `general` CLI task works in its own git worktree (`worktrees.create`, branch `gustaf/<slug>` from the project's HEAD; the project's linked directories and setup command are applied after the usual approval). A project that is not a git repository gets the private shadow copy the API subagents use (its changes are a pending review). The worktree and branch are left in place when the task ends, and the report names the branch and the changed files. Nothing is committed, merged or pushed by Gustaf and the CLI is told not to; the changes are uncommitted in the worktree, so commit them there (the merge queue refuses dirty workspaces) before merging. The worktree has no chat; it is listed with the project's workspaces.
- **Cleanup.** Default keep. With "Remove untouched subagent worktrees" on, a worktree whose task changed nothing (no edits, no commits) is removed with its branch when the run ends; a worktree whose state could not be read is never removed. A failed attempt that `retries` replaces is removed when untouched (otherwise kept, with a warning on its run). A stopped or failed run keeps whatever it did.
- **Transcript, report, tokens.** The adapter's stream is the transcript: each new tool call counts as a tool use and shows in the Background tasks column as the current step, finished calls become transcript steps (stored like any subagent message, so they survive a restart). The report is the CLI's final message (the text after its last tool call); the usual 8,000-character cap applies. Tokens are counted when the CLI reports them at the end of its run and go to the usage ledger like other subagent tokens.
- **Limits.** The type's budget applies where the CLI gives the information: wall time and tool calls (counted from new calls in the stream) stop the run mid-way; tokens are only known at the end, so a run over its token limit is marked limit-stopped after it finished; steps are not available and not enforced. A breach, and the user's own day/chat token budget (checked at most every 5 seconds while calls come in), abort the turn, which kills the CLI's process tree (`process_kill_tree` in `src-tauri/src/proc_tree.rs`: the CLI and every descendant, deepest first, only descendants of the app; Windows uses `taskkill /T /F`). The status is `limit` (own limits) or `budget` (the user's budget), as for API subagents. Stop (the run's button, or stopping the chat) does the same. Runs that were active when the app closed come back as `interrupted`. Every agent process is recorded in the process ledger (`src-tauri/src/proc_ledger.rs`, `process-ledger.json` in the app data folder, pid plus start time): on quit the app sends SIGTERM to each recorded tree, waits up to a second, then kills what is left; after a crash the next start stops the trees a dead run left behind, only when the recorded process still runs with the same start time.
- **Quota, sign-in and fallbacks.** A CLI error is classified (quota or usage limit, via the Cursor pool's `classifyQuota`; rate limit; sign-in; other) and the task fails with that reason in its report. A quota failure of a Cursor Agent account that is in the rotation pool parks it until its reset, like a chat run does. In `delegate_tasks` a task may list `fallbackProviders` (up to 3, checked against the allow-list and resolved before anything starts); with `retries` above 0 a retry after a quota, rate-limit or sign-in failure uses the next fallback provider, and stays on the last one when the list runs out or is empty; other failures retry on the same provider. A retry is a fresh run (new worktree). `fallbackProviders` is not accepted by `spawn_agent` and needs `provider` or `role`.
- **Scheduling.** CLI tasks use the same three slots and dependency and write-ownership rules as every other task; a dependant gets the report of a CLI task appended to its prompt, mixed providers included.
- **Code and tests.** `subagents.ts` (routing, `executeCli`), `cliSubagentCore.ts` (support check, access cap, failure classes, stream collector, prompts), `agentSettings.ts` (roles, allow-list, route selection), `lib/modelRouting.ts` (`providerDirectory`, Cursor pool parking), `lib/subagentWorktrees.ts` (worktree host), `components/AgentRolesSection.tsx`; `tests/cliSubagent.test.mjs` (fake CLI adapters, fake worktrees), `tests/ui/AgentRoles.test.tsx`, Rust `proc_tree::tests`, `proc_ledger::tests`.
- **Not verified.** No real Codex, Claude Code or Cursor Agent run was made: the tests use fake adapters and a fake worktree host. Not exercised for real: the flags in a subagent context (the same `codexArgs` / `claudeArgs` / `cursorArgs` as chat runs), the real worktree backend from the subagent path, the process-tree kill with a real CLI (only with `sh` and `sleep` in a Rust test), whether Codex or Claude commit or write outside their sandbox despite the instructions, the quota wording of each CLI, the Cursor pool parking with a real account, Windows and Linux. The quota patterns are the Cursor ones and are applied to every CLI. Possible leftovers: orphaned CLI processes after a crash, `gustaf/` branches that nobody merges.

## CLI-native subagents (Codex and Claude Code)

Codex and Claude Code run their own subagents inside one CLI process. Gustaf shows them as a read-only view; it does not start, route or budget them. What the event streams look like, and how sure we are:

**Codex (`codex exec --json`).**
- Verified offline with the bundled `codex-cli 0.159.0-alpha.12.1` (`codex app-server generate-json-schema --out <dir>`; `generate-ts` is the same protocol): the app-server `ThreadItem` variant `collabAgentToolCall` has `id` (call id), `senderThreadId`, `receiverThreadIds` (for a spawn: the new agent), `prompt`, `model`, `reasoningEffort`, `tool` (`spawnAgent | sendInput | resumeAgent | wait | closeAgent | sendMessage | followupTask | interruptAgent | listAgents`), `status` (`inProgress | completed | failed | interrupted`) and `agentsStates` (agent thread id to `{status, message}`; status is one of `pendingInit | running | interrupted | completed | errored | shutdown | notFound`). It is delivered in `item/started` and `item/completed`.
- Assumed (not observable without a model request): `codex exec --json` emits the same item as `{"type":"item.started" | "item.completed", "item":{"type":"collab_tool_call", ...}}` in snake_case (`sender_thread_id`, `receiver_thread_ids`, `agents_states`, `tool` as `spawn_agent | send_input | wait | close_agent`, `status` as `in_progress | completed | failed`). The parser therefore normalizes names (case, `_`, `-`) and reads both spellings. A `wait` may carry no receivers at start; the agents then only appear in the completed item's `agents_states`. Local rollout files confirm the model-facing tool names (`spawn_agent`, `wait_agent`, `list_agents`, `interrupt_agent`) but not the exec event.
- Verified on a real run (Codex 0.159.0-alpha.12.1): `codex exec --json` emits NO spawn items for a multi-agent run, only `item.started` / `item.completed` of `collab_tool_call` with `tool: "wait"`, empty `receiver_thread_ids`, empty `agents_states` and `prompt: null` (one per wait), plus `thread.started`, `agent_message` and `turn.completed`. The stream alone cannot identify agents; the real list comes from Codex's session files (next section). The event mapping above is kept for Codex versions or modes that do report them.
- Without rollout data a Codex entry has no tool-use counter and no name: the title is the first line of the spawn prompt, else the short thread id.

**Claude Code (`claude -p --output-format stream-json`).** The parent's `assistant` message contains a `tool_use` named `Task` (renamed `Agent` in newer versions) with `input: {description, subagent_type, prompt}`; the report arrives as the matching `tool_result` (a string, or text blocks) in a `user` message. Events produced inside the subagent carry `parent_tool_use_id` equal to that `tool_use` id (documented in the Agent SDK message types; not seen in this repo's fixtures before, so the test fixtures are synthetic). Sidechain `stream_event` text deltas are ignored so a subagent's text does not leak into the main answer, and its inner tool calls are counted on the subagent entry instead of becoming separate cards.

**How Gustaf shows them.**
- `nativeActivities` (`src/providers/activities.ts`) turns Codex `collab_tool_call` items and Claude `Task`/`Agent` tool calls into an `activity` part with a `subagent` field (`provider`, `agentId`, `title`, `role`, `action`, `state` running / waiting / completed / failed, `prompt` and `result` summaries, `waits`, `toolUses`, `step`); the full report is the activity's `output`. `applyActivity` merges them per agent: a spawn's call id and its later thread id are one entry, repeated `wait` calls only raise a counter (`waits`) on the agent's single entry, a finished state is kept unless the agent is sent more input, and a Claude `tool_result` completes the `Task` entry. Never zero cards: any Codex item whose type contains "collab" or "agent" that cannot become a subagent entry (an unknown tool, `list_agents`, a `wait` that names no agent yet, missing or oddly shaped fields) keeps a generic tool card with the whole item as its output (a `wait` whose result later names agents closes that card), and is counted in the raw CLI log (below). Persisted chat messages keep the `subagent` field in `parts_json`.
- Chat: `SubagentsCard` replaces all subagent activities of a message (or of the live tail) by one "Subagents" card: running / done counts in the head, one row per agent (title, state chip, a one-line result), each row expandable to the task, wait counter, tool uses and the report. An agent that was still running when the turn ended reads "Ended".
- Background tasks column: `agent/cliAgents.ts` keeps the same entries in memory (fed by `runChatCore` while the run is live; no database), so they appear in "Running", move to "Finished" when the run ends and are cleared with the trash button or on restart. Cards are labelled "Agent · Codex" / "Agent · Claude Code". "View transcript" opens the task and report (the CLIs expose no transcript), there is no Continue, and the Stop button's tooltip says it stops the whole run (it aborts the chat run; the CLI does not let Gustaf stop one subagent).

## Codex subagents from rollout files

While a Codex turn runs, Gustaf reads the session files Codex writes itself (read-only) and shows what it finds as the same `subagent` entries, so a multi-agent run gets one card per real agent, live: in the chat's grouped "Subagents" card and in the Background tasks column.

- **Where the data is.** `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<thread id>.jsonl` (`CODEX_HOME` defaults to `~/.codex`; the folder is the one `import_sources.rs` already scans for imports). The parent thread's file (its name contains the `thread_id` of `thread.started`) holds `response_item` entries `function_call` `spawn_agent` (arguments: `task_name`, `message`, `fork_turns`; output: `task_name`, with a `call_id`) and `wait_agent`. Every child agent is its own rollout file whose first `session_meta` has `parent_thread_id`, `agent_nickname`, `agent_path` (ends with the spawn's `task_name`), `source.subagent.thread_spawn{depth, agent_role}` and, for a forked child, `subagent_history_start_ordinal`. Inside: `event_msg` `task_started` / `task_complete{last_agent_message, completed_at, duration_ms}` (a child with a start but no completion is running; a later start means it was woken again), `response_item` `custom_tool_call` (name `exec`; its input is JavaScript such as `text(await tools.exec_command({cmd:"..."}))`, the shell tool) and `event_msg` `token_count{info.total_token_usage}`. A forked child's file starts with a copy of its parent's history: entries with an `ordinal` below `subagent_history_start_ordinal` (and the second `session_meta`) are ignored.
- **What Gustaf does.** `src-tauri/src/codex_agents.rs` (`codex_agents_scan(thread_id, started_at)`) finds the files, links each child to its spawn call (`task_name` against the end of `agent_path`) and returns per agent: thread id, nickname, task name, the spawn message (300 characters), state (`starting` when only the `spawn_agent` call exists, `running`, `completed`, `failed` after an `error` event, `stopped` after an aborted (interrupted) turn, `shutdown`), start, end and duration, the last agent message (4,000 characters), number of `exec` calls, the latest step (the command, 120 characters, obvious secrets replaced by `***`) and the token totals. `src/providers/codexRollout.ts` polls it about every second from `thread.started` (never two scans at once; five failed scans in a row end the polling for the turn), plus one final scan after the turn ends, and feeds the entries (action `scan`, id `codex:<parent thread>:<task name>`, the same id from the pending spawn to the end; changed entries only) through `applyActivity`, `trackCliAgents` and the chat card. A scanned entry's state and counters replace the old ones; a real spawn item for the same thread (other Codex versions) merges into it. Cards use the real start time from the file.
- **Waits.** `wait` items that name no agent are held back while the scan is on. If the scan found agents they are dropped; if it found none (files unavailable, other format, thread id never seen) they come back as one merged generic `collab_tool_call` card with the count (`args.waits`), so nothing is silently lost.
- **Lifecycle rules** (found with real rollouts, see `docs/subagents-audit.md`). `stopped` is neutral, shown as "Stopped" and not counted as running or failed: Codex interrupts the children when the parent's turn ends and writes `turn_aborted` ("interrupted"), usually a second later and sometimes never. So (1) a child without an end event is `stopped` once the parent's own last turn has ended, or when nothing was written to its file since before the current run began; (2) a `spawn_agent` call of an earlier turn whose child file is outside this run's window is history, not a "starting" card (the parent file is re-read from its start every scan, which used to bring old spawns back as cards that ticked forever); (3) two threads with the same parent and `agent_path` are one card (newest thread, card key of the spawn call); (4) when the turn is over (also when the run was stopped), `codexRollout.ts` settles every agent still running as `stopped`. Card title: the task name as words (`/root/queue_resume` becomes "queue resume"), the nickname on the secondary line, the short thread id as the last resort.
- **Privacy and limits.** Switch "Read Codex session files to show subagents" (Settings, Usage, Agents; `readCodexSessions`, default on): off means no file is opened. Only the file of the thread the app itself started (named with its thread id) and of agents whose `parent_thread_id` chain leads to it are parsed; other sessions' files are never read beyond their first line (to see `parent_thread_id`), and files older than the run are not touched at all. Only the run's start day minus one day up to now plus one day is searched (at most 8 day folders, 1000 newest files each, 400 new files per scan), no symlink is followed, nothing leaves the machine (the data goes from Rust to the UI only) and Gustaf does not store it, except that the raw CLI capture (if on) records debug lines. Per file at most 4 MB is read per call and a line over 1 MB is skipped; at most 50 agents are returned. A parent thread resumed from an old session lives in an old day folder: the children (new files, found through `parent_thread_id`) still show, but their spawn message and the pending (`starting`) card are missing.
- **Assumed, not guaranteed.** The rollout format is Codex's internal one and may change between versions. Parsing is defensive (unknown lines are ignored, missing fields leave a value out) and the scan returns `notes` for anything unexpected (no `session_meta`, unreadable lines, parent file not found, too many new files), which Gustaf writes to the raw CLI log as `rollout-note` debug lines (`rollout-error` when the scan command fails, `rollout-total` with scans, agents and held waits at the end of the turn). Verified by reading the key structure of a real Codex 0.159.0-alpha.12.1 rollout; the tests use synthetic fixtures. Not verified: a live multi-agent run through the app, the `error` / `turn_aborted` / `shutdown_complete` event names for failed and closed agents (taken from Codex's naming, absent from the sample), spawn failures (a `spawn_agent` call whose agent never starts stays `starting` until the turn ends, then reads "Ended") and a parent day folder more than a day away from the run's start.

## Raw CLI event capture (debugging)

Settings, General, "Developer", switch "Record raw CLI events" (`recordRawCliEvents`, off by default). While on, every non-empty stdout line of `codex`, `claude` and `cursor-agent` is appended before parsing (`spawnLines` `onRaw`) to `<app data>/raw-cli/<YYYY-MM-DD>.jsonl`, one JSON object per line: `t` (ISO time), `provider`, `chat` (chat id or null) and `event` (the parsed line, secrets scrubbed with `redactValue`/`redactSecrets` from `lib/exportChats.ts`) or `text` (a line that is not JSON, scrubbed too); an entry over 64k characters is clipped. Lines are buffered and written in batches (`lib/rawCliLog.ts`, Rust `rawlog.rs`: `raw_log_append`, `raw_log_clear`, `raw_log_info`); a write error never reaches the chat run. One file per day, 5 MB in total: the oldest day is deleted first, a single oversized day loses its oldest lines. The page shows files and size, "Show in Finder" (the newest file) and "Clear".

Debug lines (`debug` instead of `event`): `unmapped-collab-item` for each Codex item that mentions collab or agent but fell back to the generic card (`type`, `tool`, `status`, `reason` = `unknown-tool` / `no-agents` / `invalid`, and the item's keys), and `unmapped-total` with the count at the end of the turn. When a Codex multi-agent run shows no cards, turn the switch on, rerun, and read the `event` lines of `item.*` events with their real field names, and the `rollout-*` debug lines for the session-file scan. Tests: `tests/collabFallback.test.mjs` (shapes: snake_case, camelCase, missing fields, unknown tool, `list_agents`; log lines, scrubbing, batching), `ui/DeveloperSettings.test.tsx`, Rust `rawlog::tests`.
