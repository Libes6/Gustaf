# Subagents and background agents

Part of the [M Code documentation](../README.md).

With a writable project (not read-only mode) and a model with tool support, the main agent can start subagents with the `spawn_agent` tool (`title`, `prompt`, `type`, optional `files` and `model`). A subagent is a separate agent run: its own history (it cannot see the chat), its own model (see below), a tool allowlist by type and a budget. The main agent receives only a final report of at most 8,000 characters. Several `spawn_agent` calls in one turn run in parallel; at most 3 run at once (the limit is shared by all chats), the rest wait in a queue.

- **Types:** `explore`, `plan` and `review` are read-only (`read_file`, `list_dir`, `search`) and run in the main agent's current workspace; `general` can also edit and run commands. A subagent cannot start subagents.
- **Models (Settings, Usage, Agents):** a default model per type, else the chat's model. The main agent may pass `model` (`provider/model`, or a model id that is unambiguous) only for a model on the "Models agents may request" list, a type's model or the chat's own; anything else is refused as a tool error. Only API providers whose model supports tools can run a subagent (CLI agents such as Codex, Claude Code or Cursor run their own tools and approvals); an unavailable model falls back to the chat's model with a note in the transcript and the report. The same page sets a cheaper model for chat compaction and generated commit messages (falls back to the chat's model when it is missing).
- **Isolation:** a `general` subagent works in its own shadow copy of the project (same linked directories and setup command as the chat's copy, made from the original project, so it does not see edits the main agent has pending). Its changes show up as a separate pending review in Changes; nothing is applied until you accept. When two pending reviews of the project change the same file (two subagents, or a subagent and the main agent), the later report carries a warning naming the other one and the files, and the earlier run shows it too.
- **Budgets per run** (defaults: explore/review 20 steps, 40 tool calls, 5 min, 600k tokens; plan 15/30/5 min/500k; general 40/80/15 min/1.5M; each field can be changed per type in Settings, Usage, Agents, under hard caps): when one is exceeded the run is stopped, the transcript gets a "Stopped at its … limit" note and the report says which limit, with whatever the agent had said last. Subagent tokens also count toward the day and chat budgets: their replies are not stored as chat messages, so they are added per local day and per parent chat in the `agentUsage` setting (31 days, 300 chats) and summed into the budget gauge.
- **Plans (`delegate_tasks`):** the main agent submits up to 12 tasks (`id`, `title`, `prompt`, `type`, optional `files`, `dependsOn`, `model`). Tasks run in parallel up to the concurrency limit; a task starts only after its dependencies finished and gets their reports appended to its prompt (their file changes stay in their own pending reviews, so it does not see them in its copy). Two `general` tasks whose `files` overlap (same file, or a folder containing it), or that declare no files, never run at the same time: the later one waits. When a task fails, hits a limit or is cancelled, the tasks depending on it are skipped (setting "Cancel dependent tasks when one fails", the call can override it with `cancelDependents`). Invalid plans (duplicate ids, unknown dependencies, cycles, a model that is not allowed) are refused before anything starts. The main agent receives one merged message: a status line per task and the bounded reports.
- **Retries (`delegate_tasks`):** the call may set `retries` (0 to 2, default 0; anything else is a tool error). A task that ends `failed` (an error, not a limit stop, a budget stop or a cancel) is run again after a short pause (1 s, then 3 s), as a new run titled "<title> (retry N)" and, for a `general` task, in a fresh private copy; the failed attempt's partial changes are rejected (not left as a pending review). Dependants wait for the retries and get the final report. The merged summary says how many attempts each task took ("completed, 3 attempts") and the retry allowance.
- **Budget stop:** when the day or chat token budget (Settings, Usage, Budgets; subagent tokens count through the ledger) is exceeded, running subagents are stopped at their next step with the status "Over budget" (`budget`; the report says which budget), queued ones end as `budget` without starting, and `spawn_agent` / `delegate_tasks` are refused with a tool error naming the budget. Switch "Stop agents when over budget" (Settings, Usage, Agents, `agentSettings.stopOnBudget`, default on) off to keep budgets as warnings only. Everything else (the banner, the main agent) is unaffected. Usage is read at most every 5 s (stored messages) plus the live ledger; unreadable usage never stops anything.
- **Commands and approvals:** subagents go through the same command rules as the main agent. Deny rules block unchanged, and "ask" requests (including the shadow-copy setup command) appear as the usual approval card with a "Subagent: <title>" line, one at a time. While a request is open the chat shows a "!" badge in the sidebar (for any approval, also from the main agent), so a waiting agent in another chat is visible. Tokens are recorded like any other turn.
- **Notifications:** while M Code is in the background, a background agent that finishes, fails or stops at a limit, and any new approval request, sends a system notification (`tauri-plugin-notification`), bounces the dock icon and raises the dock badge count; focusing the window clears the badge. Can be turned off in Settings, Usage, Agents. Stopped runs do not notify.
- **Background agents panel:** top left of the chat. Running and finished subagents of the project with type, model, elapsed time, tokens, tool uses, the current step ("Waiting for approval" while one is open), a Stop button and a transcript dialog (the full stored messages, loaded when it opens and refreshed every 2 s while the run is active: the task, text, each tool call with its stored result, notes, the report) and, for a finished, failed, limit- or budget-stopped run, "Continue this agent". Stopping the main agent stops its subagents.
- **Persistence:** runs live in SQLite (`agent_runs`: id, chat_id, title, type, model, status, started_at, ended_at, tokens, tool_uses, error, report, plus provider, project, created_at, changed files and warnings; `agent_messages`: run_id, seq, role, parts_json, created_at), created by the idempotent schema in `src-tauri/src/db.rs`. Every message of a subagent (seq 0 is the task prompt) is written as it happens, bounded per message (text and results 8,000 characters, tool arguments 4,000, 48,000 per message, images dropped, secrets scrubbed like exported chats); at most 2,000 messages per run. Retention: the newest 200 finished runs plus every active one (older runs and their messages are deleted when a run is created); "Clear finished" deletes rows; deleting a chat deletes the runs it started. Runs that were queued or running when the app quit load as interrupted (and are marked in the table). The old `agentRuns` setting (50 runs with clipped steps) is migrated once into the tables (flag `agentRunsMigrated`, then the setting is emptied); migrated steps show as one message each.
- **Continue this agent:** the button (row and transcript dialog) takes a follow-up and puts a request into the chat's message box (editable, not sent): the main agent then calls `spawn_agent` with `continue_from` = the run id. The new run is seeded with a bounded summary of the old one (its task, the newest 40 tool calls, how it ended, its report) and the follow-up as its task, and runs as a normal new run (the old transcript is not replayed). Only `completed`, `failed`, `limit` and `budget` runs qualify (not running, cancelled or interrupted ones); an unknown or unfit id is a tool error. `delegate_tasks` does not take `continue_from`.

Logic: `src/agent/subagents.ts` (runtime), `subagentCore.ts`, `orchestrator.ts`, `agentSettings.ts` and `scheduler.ts` (pure: arguments, allowlists, budgets, model choice, plans, ownership, overlaps, reports, queue), `agentSettingsStore.ts`, `agentRuns.ts` / `agentRunsDb.ts` / `agentRunsModel.ts` / `agentTranscript.ts` (store, SQLite statements, the pure run model with the token ledger, and the pure transcript helpers), `lib/budgetUsage.ts` (budget check for the stop), `lib/modelRouting.ts`, `lib/attention.ts`, `components/AgentsPanel.tsx`, `components/AgentSettingsSection.tsx`; tests: `tests/scheduler.test.mjs`, `subagentCore.test.mjs`, `orchestrator.test.mjs`, `agentSettings.test.mjs`, `agentRuns.test.mjs` (also against a real SQLite via `node:sqlite`), `agentTranscript.test.mjs`, `followUps.test.mjs`, `ui/AgentsPanel.test.tsx` and `subagents.test.mjs` (the real agent loop with a scripted model and fake shadow copies).

## CLI-native subagents (Codex and Claude Code)

Codex and Claude Code run their own subagents inside one CLI process. M Code shows them as a read-only view; it does not start, route or budget them. What the event streams look like, and how sure we are:

**Codex (`codex exec --json`).**
- Verified offline with the bundled `codex-cli 0.159.0-alpha.12.1` (`codex app-server generate-json-schema --out <dir>`; `generate-ts` is the same protocol): the app-server `ThreadItem` variant `collabAgentToolCall` has `id` (call id), `senderThreadId`, `receiverThreadIds` (for a spawn: the new agent), `prompt`, `model`, `reasoningEffort`, `tool` (`spawnAgent | sendInput | resumeAgent | wait | closeAgent | sendMessage | followupTask | interruptAgent | listAgents`), `status` (`inProgress | completed | failed | interrupted`) and `agentsStates` (agent thread id to `{status, message}`; status is one of `pendingInit | running | interrupted | completed | errored | shutdown | notFound`). It is delivered in `item/started` and `item/completed`.
- Assumed (not observable without a model request): `codex exec --json` emits the same item as `{"type":"item.started" | "item.completed", "item":{"type":"collab_tool_call", ...}}` in snake_case (`sender_thread_id`, `receiver_thread_ids`, `agents_states`, `tool` as `spawn_agent | send_input | wait | close_agent`, `status` as `in_progress | completed | failed`). The parser therefore normalizes names (case, `_`, `-`) and reads both spellings. A `wait` may carry no receivers at start; the agents then only appear in the completed item's `agents_states`. Local rollout files confirm the model-facing tool names (`spawn_agent`, `wait_agent`, `list_agents`, `interrupt_agent`) but not the exec event.
- Codex does not report the child's own tool calls in the parent's stream, so a Codex entry has no tool-use counter. The child has no name: the title is the first line of the spawn prompt, else the short thread id.

**Claude Code (`claude -p --output-format stream-json`).** The parent's `assistant` message contains a `tool_use` named `Task` (renamed `Agent` in newer versions) with `input: {description, subagent_type, prompt}`; the report arrives as the matching `tool_result` (a string, or text blocks) in a `user` message. Events produced inside the subagent carry `parent_tool_use_id` equal to that `tool_use` id (documented in the Agent SDK message types; not seen in this repo's fixtures before, so the test fixtures are synthetic). Sidechain `stream_event` text deltas are ignored so a subagent's text does not leak into the main answer, and its inner tool calls are counted on the subagent entry instead of becoming separate cards.
