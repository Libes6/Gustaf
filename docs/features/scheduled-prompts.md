# Scheduled prompts

Settings, General, Scheduled prompts runs a prompt on a schedule while Gustaf is open (no background service: if the app is closed or the computer sleeps, nothing runs; keeping the computer awake is your choice and Gustaf changes no system setting). Each schedule has a title, a prompt, an optional project, a model (the current selection by default), an access mode and one of: once at a date and time, every N minutes or hours (at least 5 minutes), daily at HH:MM, or weekdays at HH:MM (local time; a DST change moves nothing: 09:00 stays 09:00, a time inside a spring-forward gap runs right after the gap, a repeated hour runs once). At most 20 schedules, stored in the settings under `scheduledPrompts`.

- **Writes to a chat** titled `⏰ <title>` in the project (the schedule's chat is reused, else one with that title, else a new one). Each run sends only the prompt to the model (earlier runs of the chat are not part of the context); the messages, tokens and tool calls are stored and counted like any chat, and tool calls appear in the action log marked "Scheduled prompt". Finished, failed and stopped-for-approval runs send a system notification while the app is unfocused.
- **Switching on is the confirmation.** A new schedule is off. Nothing runs until you switch it on, and changing the prompt, project, model, access or time switches it off again; stored data that says "enabled" without that confirmation is loaded as off. "Run now" starts a run by hand (also for a switched-off schedule) and never overlaps a run that is active.
- **Missed runs.** A run due while the app was closed happens once, on the next start, if it was due within the last 24 hours (however many occurrences were passed over); an older one is skipped and the schedule shows "missed". An interval restarts from the moment a run starts. A one-off is switched off after it has run or been missed. If a run is still going when the next occurrence comes due, that occurrence is dropped. At most two scheduled runs are active at once; others wait for the next check (every 30 seconds and when the window gets focus).
- **Safety.** Unattended runs get at most "Auto" access (a stored "full" is capped), never Computer Use, no subagents and no MCP tools (neither is passed to the loop); CLI agents (Codex, Claude Code, Cursor) run their own tools outside the app's rules, so they are read-only. With "Auto" on a project the agent works in a shadow copy and the changes wait in Changes for your review, like a normal chat. Command rules apply unchanged. A command that needs approval is never allowed automatically: the chat gets the sidebar badge, a notification is sent and a card appears in the corner of the window (Allow once or Deny); after 10 minutes without an answer the run is stopped and marked "needs attention".
- **Live in the chat.** While a scheduled run writes to a chat, the chat behaves like during your own request: if it is open (or you open it meanwhile) it shows the streamed text, tool cards, retry notice and a pending approval, the composer shows Stop (Stop and Cmd+Shift+Esc end the run, which is then marked stopped and the chat gets a note), stored messages appear as they are saved, and sending a message, compacting, rewinding, editing or deleting in that chat is blocked with the message that the scheduled run is writing to it (it clears when the run ends). The sidebar shows the running spinner on that chat, also when it is not open. An approval request is answered in the open chat; the corner card is shown only while another chat or view is in front.
- **Not covered.** Two schedules that share one chat (same title and project) can run at the same time; the chat then shows the latest of them. The UI is not smoke-tested in `tauri dev`; it is covered by component tests (`tests/ui/ChatViewLive.test.tsx`, `Sidebar.test.tsx`).

Logic: `src/lib/scheduledPrompts.ts` (pure: schedule math, validation, missed-run policy, access cap), `scheduledPromptsStore.ts`, `scheduledRun.ts` (`executeScheduledRun`, which sets the safety limits and runs the shared core `chatRunCore.ts` that interactive sends use too, and `createRunner`, both over injected dependencies), `liveRuns.ts` (store behind the live chat and the sidebar state), `scheduledApprovals.ts`, `scheduledRuntime.ts` (glue with the app state), `components/ScheduledPromptsSection.tsx` / `ScheduledPromptsRuntime.tsx`. Tests: `tests/scheduledPrompts.test.mjs` (with `TZ` switched to New York and Berlin for the DST cases), `scheduledRun.test.mjs` (the real agent loop with a scripted model, also the live state and the shadow copy), `chatRunCore.test.mjs`, `liveRuns.test.mjs` and `scheduledStore.test.mjs`.
