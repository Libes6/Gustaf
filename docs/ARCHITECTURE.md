# Architecture

M Code is a Tauri 2 desktop app: a React 19 + TypeScript frontend (Vite) and a Rust backend. User-facing behaviour is described per feature in [docs/features](README.md) (overview and setup in the [README](../README.md)); this file describes how the code is organised.

> **Paths:** the repository is an npm-workspaces monorepo. Every path in this document and in `docs/features/*.md` (`src/...`, `src-tauri/...`, `sidecar/...`, `scripts/...`, `tests/...`, `public/...`) is relative to `apps/desktop/`, and npm scripts such as `npm run test:csp` run there (`npm run <name> -w apps/desktop` from the root; `dev`, `build`, `tauri`, `test`, `test:ui`, `test:e2e` and `check` also work from the root). Other workspaces: `packages/protocol` (`@mcode/protocol`: `PROTOCOL_VERSION` and type-only skeletons of the planned phone API and WebSocket events; pure TypeScript, no React/Tauri/React Native imports; declared as a dependency of `apps/desktop` but not imported yet, since nothing serves the API) and `apps/mobile` (placeholder for the Expo app, see [TASKS.md](../TASKS.md)). The sidecar is not a workspace member: it is bundled with its own `node_modules`, so it has its own lockfile and `npm --prefix apps/desktop/sidecar ci`.

## Layers

```
React UI (src/components) ── state.tsx ── lib/ (api, data, chatSessions, context, checkpoints)
        │                                   │
        │                           providers/ (model backends)      agent/ (tool loop)
        ▼                                   ▼                              ▼
              Tauri commands (src-tauri/src/*.rs)  ◄── sidecar/ (Node helpers)
```

### Backend (`src-tauri/src/`)
| File | Commands / role |
| --- | --- |
| `db.rs` | SQLite (rusqlite, WAL). Tables: `projects`, `chats`, `messages`, `settings`, `models_seen`, `drafts` (composer text and attachments per chat or unsent new chat; removed with their chat or project) and the FTS5 index `messages_fts` (below). The schema is all `create ... if not exists`, so opening an older database migrates it. A poisoned connection mutex is recovered instead of failing every later command. Commands: `db_select`, `db_execute`, `search_messages`, `search_models` |
| `tools.rs` | Filesystem and shell: `fs_read`, `fs_list`, `fs_files`, `fs_search`, `fs_edit`, `fs_write`, `run_command`, `read_instructions` (AGENTS.md / CLAUDE.md / .cursorrules / always-apply Cursor rules, confined to the project root with `resolve_in_root`, symlinks out of it skipped, 64 KB read cap per file), `read_home_file` |
| `review.rs` | Shadow-copy review: `review_prepare` (optionally symlinks validated project-relative `linked` directories into the copy; they are skipped when copying, listing changes and deciding, so nothing is ever written back through them), `review_list`, `review_diff`, `review_decide`, `review_run` (runs a setup/test command with the copy as cwd via `tools::run_command`; approval is decided in the UI), `review_hunks`, `review_decide_hunks`, `review_finish` |
| `hunks.rs` | Pure hunk logic (no I/O, unit-tested): Myers line diff keeping line terminators, grouping into `-U3`-style hunks with content-derived ids, rebuilding a text from a chosen subset of hunks. Used by `review_hunks` / `review_decide_hunks`: accepting applies the chosen hunks to the project after the baseline check and advances the baseline by the same text; rejecting rewrites the copy only |
| `git.rs` | `git`: generic wrapper, also drives the app-managed shadow checkpoint repo. Project-repo commands for the commit flow (argument arrays only, no shell; paths validated with `resolve_in_root` and passed as literal pathspecs; repo-configured fsmonitor/textconv/external-diff commands disabled; hooks and signing never bypassed; no push/amend/force): `git_status` (branch, HEAD, changed files under the project root, unfinished merge/rebase), `git_commit_context` (bounded, fairly budgeted diff + stat + recent subjects of the selected files, for message generation), `git_commit` (commits exactly the given paths via `commit --only`, optional new branch from HEAD, rolls the branch and staging back if the commit fails). Multi-step operations are serialized per repository |
| `secrets.rs` | `secret_set/get/delete` (API keys): macOS Keychain (`security-framework`), Windows Credential Manager / Linux Secret Service (`keyring`), chosen with `cfg(target_os)` |
| `shell.rs` | Pure per-OS shell choice (`Shell::pick`: zsh on macOS, bash/sh on Linux, Windows PowerShell on Windows), its flags and script wrapper, plus `sh_quote` / `ps_quote`; used by `tools::run_command` (PowerShell has stderr read on its own pipe instead of `2>&1`). TS twin: `providers/shell.ts` |
| `computer.rs` | Computer Use: `cu_execute` (performs actions incl. `open_app` via `open -a` on macOS / `gtk-launch` on Linux (unsupported on Windows), waits for the screen to settle with a thumbnail-hash loop, returns the PNG plus front app, window title, cursor, screen-changed flag and failed step), `cu_screen_size`, `cu_permissions` (CoreGraphics/Accessibility calls only under `cfg(macos)`; elsewhere granted, `supported: false` on a pure Wayland session); `cmd` in `keypress` is Ctrl off macOS |
| `mcp.rs` | MCP stdio servers: `mcp_start` (on demand, spawn from an argument array in its own process group, login-shell `PATH`, `initialize` handshake), `mcp_request` (JSON-RPC with timeout and an optional caller key; waits while a crashed server restarts), `mcp_cancel` (by key: the waiting call returns at once, `notifications/cancelled` goes to the server, a late response finds no pending entry and is dropped; a cancel that overtakes its request still wins), `mcp_notify`, `mcp_stop`, `mcp_status`, `mcp_logs`. Newline-delimited JSON-RPC, lines capped at 16 MB, requests at 4 MB, stderr in a 400-line log. A crash after a successful handshake restarts with exponential backoff (5 in a row max, counter reset after 60 s of stable running); a generation counter makes threads of an old process harmless. Stop closes stdin, then SIGTERM, then SIGKILL of the process group; `RunEvent::Exit` stops all servers. Emits `mcp-event`; `tools_epoch`, `resources_epoch` and `prompts_epoch` count the `list_changed` notifications. Tests use `tests/fixtures/fake-mcp-server.mjs` |
| `oauth.rs` | Loopback redirect receiver for the MCP OAuth sign-in: `oauth_loopback_start` (binds `127.0.0.1` on a random port, returns it), `oauth_loopback_wait` (blocks until the authorization code, an error, the deadline or cancel), `oauth_loopback_cancel`. Accepts only `GET /callback` with `Host: 127.0.0.1:<port>`, compares `state` (a mismatch ends the attempt), other paths get 404 and are ignored, pages echo nothing, the code is never logged. Rust tests cover success, state mismatch, denial, timeout, cancel |
| `attachments.rs` | `attachments_save` (base64 images to `<app data>/attachments/<chat id>/<n>.<ext>`, magic-byte type check, at most 8 images of 10 MB, all-or-nothing, `create_new` names), `attachments_clear` (removes a chat's folder). #### Full-text search (`db.rs`)
`messages_fts` is an FTS5 table (`unicode61`, case and accent insensitive, prefix indexes; `ё`/`е` folded, see below) whose rowid is `messages.id`; it stores the readable text of a message plus unindexed `chat_id`, `role` and `model`. FTS5 and the JSON functions come with the bundled SQLite of rusqlite (`features = ["bundled"]`), so Cargo.toml needs no extra feature.
- **What is indexed:** only `text` parts of the stored JSON, joined by newlines; never images, tool calls/results or activities. User text is cleaned like `userText()` in `ChatView` (`<system_notification>` messages skipped, imported Cursor `<user_query>` unwrapped, the `<file path=...>` blocks appended for `@file` mentions cut). Compaction summaries are skipped. At most 100,000 characters per message. Malformed JSON is skipped, never an error.
- **Sync:** AFTER INSERT / UPDATE (`id, chat_id, role, content`) / DELETE triggers on `messages`, built from plain SQL functions only, so every writer keeps the index current: the JS `db_execute` bridge, imports, `ON DELETE CASCADE` from chats and projects, and older app builds that do not know about search.
- **Migration:** `init_search` runs on every start. It stores `SEARCH_VERSION` in `settings` (`searchIndexVersion`); if the table or a trigger is missing or the version differs it drops and recreates table and triggers and backfills from `messages` in one transaction, otherwise it does nothing. Bump `SEARCH_VERSION` when the extraction rules change (it is 2 since the `ё`/`е` fold, so the index was rebuilt once). A failure here is logged and does not stop the app (search then reports an error).
- **`ё`/`е` folding:** the tokenizer keeps them apart, so the indexed `text` column holds a folded copy (`ё`→`е`, `Ё`→`Е`, nested `replace()` in the trigger SQL, `fold_sql`) and `fts_match` folds the query terms the same way (`fold_yo`, which must stay equivalent). Stored messages are never changed. The fold is one character to one character, so `snippet()` of the folded text is a contiguous slice of the original: `restore_snippet` finds it in the original text (recomputed with `text_sql` for the page's rows only) and puts the original letters back, keeping the marks. A decomposed `е` + combining diaeresis is not folded.
- **Queries:** `fts_match` turns user input into FTS5 syntax by quoting every term, so operators and punctuation are plain text and cannot cause syntax errors (`"..."` is an exact phrase; other terms also match as prefixes; terms and length are capped). A term of one character is an exact token, not a prefix, and the UI does not search below two characters (`MIN_QUERY_CHARS`): a one-letter prefix would match most of the history for no useful result.
- **Paging:** `search_messages(query, projectId?, model?, limit?, offset?)` returns a `SearchPage { hits, total, totalCapped, byRecency, hasMore }`. Hits are ordered by bm25, then `rowid desc` (deterministic, so pages neither repeat nor skip unless messages are added between requests); `limit` is 40 by default, at most 100; only the first `SEARCH_CAP` (1000) hits can be paged through, and `total` is a bounded count (`limit 1001`) shown as "1000+". Each hit has a snippet with matches wrapped in `\u0001`/`\u0002`, chat title, project, archived flag, role and model. The model filter keeps messages recorded with that model (assistant replies; user messages carry none). `search_models` lists the models for the filter. Both commands run on a worker thread.
- **Performance:** FTS5 computes bm25 for every match before it can cut a page, and a sorted subquery that also selects `snippet()` computes it for every match too. So the page query ranks on the index only (no snippet), and snippets for the page's rows come from one extra pass limited to their id range (`+rowid in (...)` so SQLite does not turn the list into one index seek per hit; per-hit seeks were the dominant cost). When a query matches more than `RANK_UP_TO` (5000) messages it is "very common": hits are ordered newest first (`byRecency`), which stops after one page. Measured on 30,000 synthetic messages in a debug build (unoptimised SQLite): a query matching every message 4-13 ms for the first page (before the split: about 4 s, and ~290 ms with only the snippet split), 3,750 ranked matches ~20 ms, rare terms 1-2 ms. `cargo test --lib search_perf -- --ignored --nocapture` reproduces it.
- **UI paging:** `SearchPalette` requests pages of 40; "Load more" (also reached by Arrow Down on the last row) asks for `offset = hits.length`, pages merge with `mergeHits` (de-duplicated by message id), and every new search or filter change bumps the request counter so late pages and late first pages are dropped. When a project is open the filters row offers an "Only this project" checkbox.

## Key flows
- **Chat request:** `ChatView` → `providers/index.ts` picks a backend → API providers go through `agent/agent.ts` (tool loop calling Tauri commands); CLI providers stream via the shell plugin.
- **Writable project:** `review_prepare` copies sources to an app-managed directory; the agent edits the copy; `ChangesPanel` shows diffs; `review_decide` applies files after a baseline check; checkpoints allow rollback.
- **Commit accepted changes:** `ChangesPanel` records each accepted file (`acceptedFiles`) and offers `GitCommitDialog` while any of them is still dirty in git. The dialog loads `git_status`, pre-selects the accepted files, optionally generates a message through `getAdapter(selected provider).turn` (read-only, no tools, usage recorded like other turns) from `git_commit_context`, and calls `git_commit` with only the ticked paths.
- **Subagents:** `runLoop` offers the host's tools (`spawn_agent`, `delegate_tasks`; the allowed models are named in their descriptions) only when `RunOptions.subagents` is set (main loop), tools exist and access is not read-only; the calls of one turn start together and their reports come back as the tool results. `spawn` (subagents.ts) validates the arguments, picks the model (`selectModel`: explicit `model` from the allow-list, else the type's default from `agentSettings`, else the parent's; `resolveModel` turns it into an adapter and an unusable one falls back to the parent's with a note), checks the day/chat budget (refuses with a tool error when `stopOnBudget` is on and it is exceeded), seeds a `continue_from` prompt from the stored run, registers a run in `agentRuns` (with the parent's `chatId`; run row and messages are written to SQLite), waits for a slot in the shared `Scheduler` (3 at a time), then runs a child `runAgent` with its own history, `toolNames` (allowlist by type), `maxSteps`, `systemExtra` and no `subagents` (no recursion). `delegate` validates the whole plan (and every task's model) first, then `runPlan` starts ready tasks up to the scheduler's concurrency, never two `general` tasks with overlapping `files` at once, appends dependency reports to dependants' prompts, skips dependants of a failed task when `cancelDependents`, and returns `mergeReports`. Budgets come from `resolveBudget(type, settings.budgets)`; each reply's tokens go to `recordAgentTokens` (ledger per day and parent chat, added to the stored-message totals in `Budgets.tsx` via `withExtraTokens`). Read-only types run in the parent's workspace; `general` gets `prepareShadowCopy(projectRoot)` (so `review.prepare`/`finish` as for the chat, a separate review per agent) and, when done, `review.list` is compared across reviews to warn about overlapping files. Budgets (tool calls, tokens, wall time, and the user's day/chat budget checked at every step boundary) abort the child's own `AbortController`; `delegate` wraps each task in `runWithRetries` (new run and private copy per attempt, the failed attempt's changes rejected); the parent's signal is linked to it. Approvals use the parent's `approve` (wrapped by `serializeCalls`, tagged with `agent`), so deny rules and the access mode apply unchanged. Parent chat state (messages, stream, retry) is never shared; token usage goes through `app.recordTokens`.
- **MCP tools:** `runLoop` (main loop, models with tools) calls `loadMcpToolset` for the servers in scope (global + this project), appends their namespaced definitions to the tools and an MCP note to the system prompt. A call to an `mcp__` tool goes through `runMcpTool`: the policy is read from settings at call time (`decideMcp`: read-only mode blocks tools not marked read-only; otherwise per-server/per-tool allow or an `mcp` approval request), then `callMcpTool` and `mapCallResult` (or `callMcpResourceTool` for the built-in resource tools, whose policy keys are their bare names). Aborting the run cancels the call (see `mcp_cancel`). The action log records it like any tool. CLI providers are not involved: they read their own MCP configuration.
- **Search:** Cmd+K (`App.tsx`) or the sidebar button opens `SearchPalette`; typing is debounced, only the newest request updates the list, a hit calls `openChatAt(chatId, projectId, messageId)`, and `useMessageJump` in the chat view scrolls to the message (or the nearest one if it was removed).
- **Canvas:** assistant messages with a `tsx-canvas` fence become cards; revisions are derived from stored messages; code runs in an opaque-origin iframe. An artifact may have several files (`// file:` sections), a Changes tab diffs two revisions, and the document can be exported as standalone HTML.

## Security
The webview runs under a strict CSP (`app.security.csp` / `devCsp` in `tauri.conf.json`) and a narrowed capability set (`capabilities/default.json`). `'unsafe-eval'` and inline styles are allowed only because the canvas `srcdoc` iframe inherits the parent policy; the network goes through the http plugin (IPC) and its scope allows plain http only for local and private-network hosts. Details, tradeoffs and the manual checklist: [features/security.md](features/security.md).

## Conventions
- Validation: `npm run check` (i18n, `tsc`, node tests, UI tests, end-to-end tests, `cargo test`). CI (`.github/workflows`) runs it on macOS, Windows and Linux. Platform-specific Tauri config: `tauri.macos.conf.json` (overlay title bar, `app`/`dmg`), `tauri.windows.conf.json`, `tauri.linux.conf.json` (bundle targets), merged over `tauri.conf.json`; shell scopes per OS in `capabilities/`. Rust tests must not assume `/` paths or POSIX tools: gate them with `cfg(unix)`.
- Tests live in `tests/*.test.mjs` (Node test runner, pure logic; `npm test`); `tests/canvas.html` is a dev-only fixture.
- Component tests live in `tests/ui/*.test.tsx` (Vitest + Testing Library + jsdom, `npm run test:ui`, config in `vitest.config.ts`, type-checked by `tsc` through `tsconfig.json`). `tests/ui/setup.ts` replaces every `@tauri-apps/*` module the components import; `tests/ui/tauri.ts` is the fake backend (`mockInvoke({ command: value | fn })`, `mockSettings`, `callsOf`; unknown commands answer like an empty backend); `tests/ui/render.tsx` provides `renderApp(ui, makeApp({...}))` with a fake app state (`AppContext` is exported from `state.tsx` for this; functions not given are spies). Covered: `Sidebar`, `Settings` navigation and pages, `Composer` and `ContextChip`, `ApprovalCard`, `GitCommitDialog`, `SearchPalette` (fake timers for its debounce). Not covered: `ChatView` as a whole (run loop, streaming), `ChangesPanel`, `ModelPicker` details, canvas, importers UI.
- `tests/csp.test.mjs` builds the frontend and checks it against the CSP in `tauri.conf.json` (static scan, plus headless Chrome when installed); see [security](features/security.md).
- End-to-end tests live in `tests/e2e/*.test.mjs` (`npm run test:e2e`, about 20 s; also part of `npm run check`). They run the real production build (`vite build`, served from a private 127.0.0.1 port with the production CSP as a response header, like Tauri serves `index.html`) in the locally installed Chrome through `playwright-core` (no browsers are downloaded; `CHROME_BIN` overrides auto-detection; the runner exits 0 with a message when no Chrome or too old a Node is found). Nothing Tauri exists in the page, so `tests/e2e/tauriInit.js` is injected before any app code: a fake `window.__TAURI_INTERNALS__` whose `invoke` calls a binding into the test process, where `tests/e2e/fakeBackend.mjs` answers every command. Choices: the database is the real SQLite engine through Node's built-in `node:sqlite` (Node 22.13+, no extra dependency, schema read from `src-tauri/src/db.rs`, so there is no second copy of the migrations), only the FTS5 index is replaced by a substring scan behind `search_messages`; `plugin:http|fetch*` implements the plugin's wire protocol on top of `FakeProvider`, a scripted OpenAI-compatible endpoint (`provider.reply({ text | toolCalls, hold })`, `hold` keeps a stream open until `release()`); secrets, review/git/shell commands and the save dialog are small stubs (shell commands are recorded, never run); unknown commands answer `null`. `harness.mjs` gives every scenario a fresh browser context and backend and fails it on any console error (this includes CSP violations), any `Refused to` text or uncaught page exception (`guard.test.mjs` proves that it does). Waiting is always on locators or polled conditions, never fixed sleeps. Screenshot, Playwright trace and the backend call log of a failed scenario go to `tests/e2e/artifacts/` (git-ignored; CI uploads it on failure). Scenarios: first-run onboarding and provider setup, streaming with the live token meter, message actions (edit and resend, delete), projects, Cmd+K search and jump, approval card (Allow and Deny), canvas card in its iframe, every settings page, JSON export then import, theme persistence. Not covered: WebKit, the Rust commands themselves (`cargo test`), real network and the real FTS index.
- All user-visible strings go through `src/i18n`.
- Node version: see `.nvmrc`.
